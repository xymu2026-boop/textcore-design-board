# CODEX REVIEW · TextCore 后续项目计划 v1.0（前端优先）

> 审查时间：2026-06-12  
> 审查对象：`00_产品设计/开发计划/TextCore_后续项目计划_v1.0_前端优先.md`  
> 审查角色：CodeX，偏前端落地 / 工程执行 / 风险控制

## 1. 总体判断

我认同“前端优先”的大方向。

当前后端流水线已经能跑通真实样本，内容质量调优会是长期、多轮、主观判断较强的工作；前端收尾则边界更清楚，能较快形成一个可演示、可验收、可承接后续质量调优的稳定底座。因此，先做阶段一 A1-A5 是合理的。

但阶段一需要避免两个风险：

1. 把“高保真还原”误解成单纯照抄 demo，而忽略真实数据、长标题、长正文、真实复核数量带来的布局压力。
2. 为了“只用真实 API”而让开发体验变差。应移除静默假数据回退，但可以保留显式、受控的开发样例机制，例如独立 seed 脚本或测试 fixture，不应在 API client 失败时自动造数据。

## 2. 对 A1-A5 拆解的意见

### A1 清理假数据回退

认同，且应作为阶段一第一步。

上一轮 `apps/web/src/api/demo.ts` + `client.ts` fallback 的问题不是“有 demo 数据”，而是“API 失败时静默显示假课程”。这会误导验收，也会掩盖真实后端连接问题。

建议验收标准补充：

- `apps/web/src/api/client.ts` 不再 import demo/fallback 数据。
- API 失败时在工作台、课稿库、详情页分别显示明确错误：后端未连接、请求失败、课程不存在。
- 开发样例数据只允许通过后端 seed / SQLite / `data/processed` 进入 API，而不是前端硬编码。
- 前端错误态必须有“重试”按钮。

### A2 详情页高保真优化

认同这是阶段一最高优先级，但六项里建议重新排序。

我建议优先级为：

1. 数据真实性与标题规范：标题、讲师、课型、文件名、状态、字数比例必须正确。
2. 详情页三栏阅读骨架：左侧 C 段常驻导航 / 中间正文 / 右侧资源抽屉或浮层入口，先稳定主结构。
3. 四档版本 + 原文对照：版本切换不能破坏滚动位置；原文对照应按当前 C 段同步，而不是整篇错位。
4. 资源上下文联动：知识点、素材、复核、旁征博引要能从当前段落或标签打开对应内容。
5. 复核标记与旁征博引微交互：hover 气泡、作者/作品浮层、右侧详案。
6. 阅读排版细节：字号、行距、段距、最大宽度、移动端降级。

计划文档里第 2 点写“左侧 C01-C09 常驻章节侧栏替代当前下拉”，方向对，但要注意：之前用户已经明确喜欢原版 demo 的三栏详情页，左侧导航应恢复为常驻侧栏；顶部章节下拉可以保留为辅助，但不能取代左侧常驻导航。

另一个建议：A2 不应一次性做成大任务，建议拆成 4 个 CodeX 子任务：

- A2.1 详情页布局骨架：左侧常驻 C 段导航 + 中间阅读 + 右侧抽屉/浮层入口。
- A2.2 版本与原文对照：四档 tab、字数比例、当前 C 段同步对照。
- A2.3 资源联动：知识卡、素材、复核、旁征博引从摘要标签和正文标记打开。
- A2.4 视觉 QA：按 demo 截图逐项调间距、字号、卡片、阅读宽度。

这样每个 diff 更容易审查，也更不容易把详情页再次改乱。

### A3 其余页面打磨

合理，但优先级应低于 A2。

建议把 A3 分为：

- 工作台：上传区、最近处理、SSE 进度、失败态。
- 课稿库：真实列表、筛选、状态、查看/导出入口。
- 知识资产页：先做“从课程聚合入口”的过渡版，不要过早做复杂知识库。

知识资产页当前依赖后端聚合能力，若后端 API 未做，前端不应硬凑假资产。建议阶段一只保证入口和空态，真正聚合放到阶段三 C1。

### A4 交互与状态完善

合理，但需要补两个容易遗漏的验收点：

- 浏览器刷新详情页后，能重新从 API 拉课程，不丢状态。
- 后端处理中或失败时，前端不能卡在“假完成”；SSE 中断要有可理解提示。

“上一篇 / 下一篇”建议阶段一先弱化为“返回课稿库”，等有课程排序上下文后再实现真实相邻跳转。否则容易写出误导性逻辑。

### A5 前端验收

合理。建议验收产物固定为：

- 四页截图：工作台、课稿库、详情页、知识资产。
- 详情页至少两套真实课程截图：醉叟传实验02、寒假第七讲实验02。
- 一份差异清单：与 `docs/prototype` 仍不同的地方，标注“有意差异 / 待修差异”。
- `npm run check`、`npm run build` 通过。

## 3. A2 六项优先级是否认同

方向认同，但顺序建议调整。

原计划六项中，“复核标记 hover”和“作品旁征博引浮层”属于精细交互，应放在详情页主体结构之后。当前最该先稳住的是：

1. 三栏布局和长文阅读宽度。
2. C 段导航定位与滚动体验。
3. 四档版本字数比例和真实正文渲染。
4. 当前 C 段原文对照。

原因是：详情页核心是阅读。如果主体阅读区、导航、对照先不稳，再精致的浮层也会显得像装饰。

## 4. 阶段二内容质量方法是否可行

可行，而且“6 篇矩阵”是正确方法。

建议把 6 篇矩阵进一步结构化成固定评估表，避免每轮只凭感觉：

- 原文字数。
- S3 分块数。
- 保真版字数 / 保留率。
- 精简版字数 / 保留率。
- 学习版字数 / 保留率。
- 结构提纲字数 / 保留率。
- 知识卡数量。
- 作文素材数量。
- 复核标记数量。
- 古文命中数量。
- 人工读感：主线完整、老师判断是否保留、作文点评是否可复用、文言文是否可靠。

阶段二可以先只盯两个指标：

- 保真版：不要漏，宁可稍长。
- 精简版：能作为妈妈默认阅读材料。

“学习整理”和“结构提纲”可以后调，因为它们更像二级产物。

## 5. 分工与边界是否清晰

基本清晰。

建议再强调三条执行边界：

1. CodeX 做阶段一时默认只碰 `apps/web/`，除非 inbox 明确授权后端字段调整。
2. `docs/prototype/` 只能只读参照，不要改。
3. 如果发现 API 字段不足，CodeX 应先在 OUTBOX 写“需要后端补字段”，不要直接改 schema 或后端契约。

另外，“不提交 git”是对的。当前多 AI 协作里，CodeX 实现、Claude 审查提交的模式应该继续保持。

## 6. 更优顺序与并行机会

建议阶段一顺序改为：

1. A1 清理前端假数据回退。
2. A2.1 详情页骨架恢复。
3. A2.2 版本与原文对照。
4. A2.3 资源联动与旁征博引。
5. A3 工作台 / 课稿库打磨。
6. A4 状态与错误处理。
7. A5 截图验收。

可并行机会：

- A3 工作台/课稿库可以和 A2.3 并行，但不建议和 A2.1 并行。A2.1 会影响全局布局和样式 token，先让它稳定。
- A4 中的错误态、空态可以和 A1 一起做，因为清理 fallback 后必须补错误态。
- 知识资产页不建议在阶段一深做，应等 C1 后端聚合 API 明确后再做完整版本。

## 7. 我建议新增的前端差距清单

计划中已有核心项，但建议补以下遗漏：

- API 失败态：工作台、课稿库、详情页、导出失败分别怎么显示。
- 处理中课程详情：课程还没完成时，详情页展示哪些内容，哪些按钮禁用。
- 导出体验：导出中、成功、失败、下载文件名。
- 长标题折行：真实课程标题很长，必须避免撑破首屏。
- 真实复核数量很多时的抽屉性能与布局。
- 移动端最低可读：第一版不做手机上传，但手机阅读结果页应不崩。
- 打印/导出入口：妈妈可能会打印，导出按钮和勾选项要稳定。

## 8. 结论

这份计划可以作为后续执行主线。

我的建议是：不要把阶段一扩大成“前端全部完美”，而是聚焦“真实 API + 详情页阅读体验 + 主要状态闭环”。只要 A1、A2、A4 做稳，就可以得到真正可用的 v0.9。A3 的知识资产页和更精细的视觉打磨可以稍微靠后，避免阶段一拖太长。

推荐下一条 CodeX 任务从 A1 开始：

> 移除 `apps/web/src/api/demo.ts` 和 API 失败静默 fallback；补齐工作台、课稿库、详情页的 API 错误态和重试；保持真实 API 可用时体验不变；`npm run check && npm run build` 通过。
